# Контракт чтения архива tgcli, версия 1

**Статус:** проект контракта. Публичной команды экспорта пока нет; её
реализация принадлежит `~/code/tgcli`. В v1 передаются только впервые
архивированные сообщения. Правки и удаления не отслеживаются.

## Почему без очереди

В таблице `messages` tgcli уже есть глобальный `id INTEGER PRIMARY KEY
AUTOINCREMENT`. Он возрастает при добавлении строки независимо от даты
Telegram-сообщения: догруженная старая история тоже получает новый `id`.
Экспортёр может читать архив через отдельное read-only соединение SQLite WAL,
как это уже делают архивные команды tgcli. Новый процесс не открывает вторую
Telegram-сессию и не получает прямой доступ к записи в базу.

Потребитель периодически запрашивает следующую ограниченную порцию записей и
хранит последний успешно обработанный курсор. Это **поток по требованию**;
брокер сообщений и постоянно запущенный producer в v1 не нужны.

## Операции

1. `head(account)` возвращает `archiveId` и текущий верхний `id` архива `H`.
   `archiveId` — постоянный идентификатор конкретного архива; при создании
   нового архива он меняется. Курсор другого архива отклоняется.
2. `scan(account, after, until=H, limit=N)` возвращает сообщения с
   `after < id <= H`, упорядоченные по `id`, и `nextCursor`. Потребитель
   проходит снимок порциями до `H`. Пропуски в `id` допустимы.
3. После этого `scan(account, after=lastCursor, limit=N)` без `until`
   выдаёт новые архивные строки. Пустой ответ означает «сейчас новых строк
   нет»; потребитель повторяет запрос позднее. Новый курсор не уменьшается.

Публичная форма может быть CLI с JSON-порциями; точное имя команды и размер
порции определяются при реализации в tgcli. Она должна сохранять те же
гарантии. Внешний индексатор не читает таблицы tgcli напрямую.

## Запись

```json
{
  "version": 1,
  "archiveId": "synthetic-archive-id",
  "cursor": 42,
  "accountId": "synthetic-account-id",
  "chatId": "synthetic-chat-id",
  "topicId": null,
  "messageId": 17,
  "sourceRef": "tgcli://account/chat/message",
  "messageDate": "2026-10-05T09:00:00Z",
  "archivedAt": "2026-10-05T09:00:03Z",
  "text": "Синтетический пример",
  "media": []
}
```

`cursor` соответствует внутреннему `messages.id`, но потребитель не
интерпретирует его как время или ID Telegram-сообщения. Пара
`(accountId, chatId, messageId)` идентифицирует оригинал и ключ
идемпотентной записи в индекс. `sourceRef` — логическая ссылка на оригинал
через tgcli; публичный Telegram URL добавляется только когда он существует.
Содержимое вложенных файлов в v1 не передаётся.

## Повтор и завершение порции

- Индексатор сохраняет курсор **после** успешной записи и проверки всей
  порции в OpenViking. При сбое повторяет порцию; повтор не создаёт дублей.
- Если в ограниченном диапазоне больше нет строк, `nextCursor` достигает
  `H`, даже если некоторые номера были пропущены или удалены. Поэтому переход
  от начального прохода к чтению новых строк не зависает.
- При замене архива, несовпадении `archiveId` или курсоре выше его текущей
  верхней границы индексатор останавливается и требует пересоздания проекции.
- Для ежедневной сводки используется `messageDate`, а не момент архивации:
  старая история может попасть в архив сегодня. Поздно пришедшие сообщения
  учитываются при проверке покрытия соответствующего дня.

## Ограничения v1

- Правка существующей строки сохраняет её `id` и **не попадает** в поток.
- Удаление убирает строку. Уже проиндексированный текст **может остаться** в
  OpenViking; строка, удалённая до чтения порции, может не попасть в индекс.
  Пока нет обработки удалений, проекция не объявляется точной копией
  текущего состояния Telegram.
- Архив охватывает только сообщения, которые tgcli успел получить. Экспорт
  должен дополнительно сообщать число известных чатов, отключённую
  синхронизацию, ошибки фоновых задач и свежесть приёма. Эти показатели не
  доказывают полноту истории, но делают пробелы видимыми.

Правки, удаления и строгую сверку актуального состояния следует добавить в
следующей версии отдельным решением. Для них понадобится журнал изменений
или периодическая сверка; простой курсор `messages.id` этого не решает.
